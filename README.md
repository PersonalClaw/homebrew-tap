# PersonalClaw Homebrew tap

The Homebrew formula for [PersonalClaw](https://github.com/PersonalClaw/PersonalClaw) — a
self-hosted personal AI agent you chat with via Slack, a web dashboard, or the CLI.

## Install

```bash
brew tap PersonalClaw/tap
brew install personalclaw
```

Or in one step, without tapping first:

```bash
brew install personalclaw/tap/personalclaw
```

Then:

```bash
personalclaw setup      # create ~/.personalclaw and pick a provider
personalclaw gateway    # dashboard on http://localhost:10000
```

Upstream's [Getting started](https://github.com/PersonalClaw/PersonalClaw/blob/main/docs/guides/getting-started.md)
guide takes it from there. Homebrew is one of several install paths — `uv tool install
personalclaw` is upstream's recommended one, and the container images need no Python at
all. See the [install matrix](https://github.com/PersonalClaw/PersonalClaw#install-matrix).

## What the formula does

- Installs the **PyPI sdist**, pinned by version and verified by `sha256`.
- Builds a dedicated virtualenv under the keg's `libexec` with `python@3.13`, resolving
  PersonalClaw's Python dependencies from PyPI and preferring published wheels.
- Puts a small `personalclaw` launcher in `$(brew --prefix)/bin`.

The venv is deliberately PersonalClaw's own rather than Homebrew's shared
`site-packages`: PersonalClaw installs an app bundle's declared Python dependencies into
its interpreter at runtime, so it needs an environment it is allowed to write to.

### Why the venv is built in `post_install`

Because the dependency closure ships prebuilt Mach-O dylibs. After `install`, Homebrew
rewrites the dylib ID of every `MH_DYLIB` file in a keg to an absolute path under
`$(brew --prefix)/opt/...`. Measured: this closure contains **22** such files — `nh3`,
`cryptography`, `tree-sitter-language-pack`, Pillow's 17 bundled codec `.dylibs`, and
pypdfium2's `libpdfium.dylib` — all linked with no header padding. The first rewrite fails:

```
Failed changing dylib ID of .../site-packages/nh3/nh3.abi3.so
  from @rpath/nh3.abi3.so
Updated load commands do not fit in the header
```

and `brew install` exits 1 even though the keg installed completely (9,895 files, 236 MB).
There is no formula-level opt-out — `fix_dynamic_linkage` walks the whole keg and runs
unconditionally for a source build. But Homebrew orders its final steps `link` ->
`install_service` -> `fix_dynamic_linkage` -> `post_install`, so a venv created in
`post_install` does not exist when the scan happens. Nothing is lost: a dylib ID is
meaningless for a Python extension module, which is `dlopen`'d and never linked against by
name.

### The trade-off, stated plainly

**This install is not hermetic.** It needs network during `brew install`, and two installs
on different days can resolve different dependency *patch* versions.

The usual Homebrew idiom for a Python CLI is `virtualenv_install_with_resources`, with one
checksummed `resource` stanza per dependency (generated by `brew update-python-resources`).
That is hermetic, and it was ruled out here not on cost but because **it cannot work**.
`virtualenv_install_with_resources` installs every resource **from source** (`--no-binary
:all:`), and this closure has a member with no buildable source: `pdfplumber` requires
`pypdfium2`, whose build is a *prebuilt* PDFium — a Chromium component, with no Homebrew
formula to link a system copy against. So the vendored route would be roughly 70
hand-maintained stanzas, a `depends_on "rust" => :build` for `nh3` and `cryptography`, a
source build of numpy, lxml and `tree-sitter-language-pack` on every single install — and
then still fail. (Those stanzas would also need regenerating every release, where a stale
one is an install failure rather than a warning.)

So the formula pins and verifies the artifact that is actually PersonalClaw, and lets pip
resolve the rest inside the bounds the release declares. Those bounds are not nominal:
upstream upper-bounds every specifier with a known-breaking next major, each with the reason
written beside it — 0.1.3's wheel asks for `croniter<7`, `websockets<17`, `reportlab<5`,
`python-docx<2` and so on. That is what keeps "resolved at install time" from meaning
"resolved to anything at all". Functionally this is `pip install personalclaw` — a
first-class supported path in upstream's install matrix — wrapped in a managed venv, a
versioned keg and `brew upgrade`. It does not claim more than that.

If you want a hermetic, fully pinned install, use the Nix flake in the main repository
(`nix profile install github:PersonalClaw/PersonalClaw#personalclaw`) or a container image.
Those get reproducibility by resolving from a locked package set instead of from PyPI.

## Cutting a new version

A release bump touches exactly two lines of `Formula/personalclaw.rb`: `url` and `sha256`.

The `url` cannot be edited by hand from the version alone. `brew style`'s
`FormulaAudit/PyPiUrls` cop requires the opaque `files.pythonhosted.org/packages/<a>/<b>/<digest>/`
form and rejects the predictable `packages/source/p/personalclaw/` path, so the new path has
to be read back from PyPI. This prints both replacement lines:

```bash
VERSION=0.2.0
curl -s "https://pypi.org/pypi/personalclaw/${VERSION}/json" | python3 -c '
import json, sys
u = [u for u in json.load(sys.stdin)["urls"] if u["packagetype"] == "sdist"][0]
print(f"""  url "{u["url"]}"\n  sha256 "{u["digests"]["sha256"]}\"""")'
```

Paste them over the existing two lines, then re-check:

```bash
brew style Formula/personalclaw.rb
# Installing a formula BY PATH is refused ("Homebrew requires formulae to be in a tap"),
# so point the tap at this working copy and install through it.
brew untap PersonalClaw/tap 2>/dev/null
brew tap PersonalClaw/tap "file://$PWD"
brew install personalclaw/tap/personalclaw
brew test personalclaw
```

Only publish a bump for a version that is **already on PyPI**. The formula's `sha256` is a
digest of a published file; there is nothing to point it at before the release job has run.
`brew livecheck personalclaw` reports when PyPI has moved ahead of the formula.

## Verification

`.github/workflows/formula.yml` runs on every push and pull request, and weekly on a
schedule because an install-time-resolved formula can break with nobody touching it. One
job, on a **clean GitHub-hosted macOS runner** — a fresh machine per run, which is the
closest available stand-in for the "clean mac" this formula has to work on. It runs `brew
style`, taps the checkout under test, runs the real `brew install
personalclaw/tap/personalclaw` and `brew test`, and asserts the bundled dashboard arrived.

There is no Linux job. Homebrew on Linux refuses an x86_64 CPU without SSSE3, which rules
out a QEMU-emulated amd64 container on Apple Silicon (measured: `Error: Homebrew's x86_64
support on Linux requires a CPU with SSSE3 support!`, and `QEMU_CPU=max` does not help
because the check reads `/proc/cpuinfo`, which shows the host's ARM CPU). `brew` is also
absent from GitHub's `ubuntu-latest` PATH.
